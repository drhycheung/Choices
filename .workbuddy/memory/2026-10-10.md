### #7 首页加载慢 —— 诊断结论与直觉相反，值得记住

用户报"开始页要等几秒才出题材卡"。**实测推翻了最初的猜测**：

| 怀疑 | 实测 | 结论 |
|---|---|---|
| JSON.parse 慢 | 6 个场景全 parse 完只要 **0.6ms** | 完全不是瓶颈 |
| 网络慢 | `responseEnd` = **3.2ms**（file://） | 不是瓶颈 |
| HTML 太大 | 290KB，但要逐项排除才发现真凶另有其人 | 部分原因 |
| **渲染阻塞资源** | 去掉 3 个 `<script>` 后41ms vs 完整页 1244ms | **真凶** |

真正原因是**三个 `<script src>` 没有 `defer`**，阻塞 HTML 解析；284KB 内嵌 JSON 是次要因素（它同时也拖慢了解析，但删掉它 alone 不够）。

修复：
- `<script src>` 全加 `defer`（`player.js` 本来监听 `DOMContentLoaded`，与 defer 兼容）。
- `index.html` 只内嵌 2KB manifest（290KB → 12KB）；场景与结局由 `tools/embed-scenarios.py` 生成到 `embed/*.js`，运行时**动态注入 `<script src>` 按需加载**（实测 file:// 下可用；**ES module 不行**，会被 CORS 拦）。
- 首屏只用 manifest 里的 title/hook 渲染封面，**场景数据等玩家按 START 才加载**。
- 效果（热缓存同口径）：**DOMContentLoaded 228ms → 12ms**。

**踩过的四个坑（都真实发生过）**：
1. `embed/*.js` 最初依赖单独的 `bootstrap.js` 建容器，某版 player.js 忘了先加载它 → 所有数据文件在 `undefined.scenarios` 上抛错。**改成每个文件自带幂等初始化**，谁先被注入都行。
2. `loadEmbedScript` 写成"注入后在容器里读"却**漏掉注入这一步**，永远读到 undefined。
3. 并发调用时第二个请求会在第一个数据写入 window 前就读 → `beginPlay` 拿空结局校验，报「endings 缺少 condition」。用 **Promise 队列串行化**。
4. `endings-core.json` 顶层包了一层 `{"endings": {...}}`，直接塞进 runtime 会变成 `endings.endings`，多一层包装 → 校验器报「缺少 condition」。embed 脚本里**剥掉外层**。

**测量方法教训（重要）**：
- **无头浏览器冷启动 ≈ 2.4 秒，与网站代码无关**。同一页面第 1 次 goto 2441ms、第 2/3 次 **34ms**。所有"3 秒"测量都是首次冷启动数字。
- **必须先预热再测**，并用 A/B（git stash 切换）同口径对比，否则会得出完全错误的结论。我一度用冷启动数字得出"改动让体感变慢"的错误判断。
- 逐项排除法要真正互斥：先前每个 case 都保留了其他资源，测出来的"都快"是假的（真实慢源还在）。

### #4 导出学习报告

结局页底部新增导出区（虚线紫框），两种格式，纯客户端 `Blob` + `<a download>`，无后端：
- **Markdown**（给学生/打印/提交）：分数总账表格 + 全部 15 步（章节 + 节点叙事 + 选择 + 逐维度增减表 + 为什么）+ 完整结局复盘（trigger/tradeoff/canvas/legal/利益相关者/补救/反思）+ 结尾声明"本局无随机数"。
- **JSON**（给老师批改/二次分析）：全量决策轨迹、scoreLedger（含每个维度的 movedBy）、finalScores、debrief。

导出内容全部来自 `state.history` 真实轨迹，不重新计算结论；`exportSteps()` / `exportLedger()` 为两种格式共用同一事实来源。
自检：`movedBy` 条数与 steps 独立统计一致（3 条）、delta 求和（2+1+1=4）与终局净变化 +4 吻合。

**测试脚本的坑**：Playwright 通关循环要给足次数（实际需 **34 次**点击，给 30 次会误判"没到达结局"）；DOM 重建后 `$$` 拿到的句柄会失效（"Element is not attached to the DOM"），每轮重新用 `>> nth=N` 查询；IIFE 闭包内的函数无法从 `page.evaluate` 直接调用（`buildMarkdown is not defined`），要验证导出须用真实下载事件或注入钩子。

## 教学清晰度审计（承接 10-09 的因果链条工作）

用户反馈：局内因果已清楚，但**结局复盘里"分数的增减"没标出具体是哪一项在加/减**。排查后发现两个真实缺陷（不是文案问题，是代码问题）：

1. **风险三维被加总成一个数字**：`riskAttribution()` 调 `topMoves(keys,...)` 把 national_security + legal + ethics 求和，学生看到「+4」无法知道是哪条风险线涨了。
2. **颜色按正负号上色而非好坏**：`.attr-delta.up { color: var(--green) }` —— 风险 +4 会被涂成**绿色**，与直觉完全相反。

### 修复（提交 b3d2435，已推 main）
- 新增 `scoreLedger()`：结局页最前面放「分数总账」，六个维度**逐行**列 `开局 X → 终局 Y` + 带符号净变化 + 方向词（更糟/更稳/更好/更弱）+ 好坏配色（由 `higherIsRisk` 决定，绝不由符号决定）。
- 每行附「改动来源（按幅度排序）」列出推动该维度的步骤；未被改动时显式写「整局没有任何一步改变这一项」。
- `canvasAttribution()` / `riskAttribution()` 全部改为逐维度；删除死代码 `topMoves` / `movesList`（grep 确认零调用点后才删）。
- **章节标签（act）**：发现第 13/15 步选项文字完全相同（「不融资，靠订阅收入自然增长」）无法分辨，故在归因行加章节标签 + 新 CSS `.attr-act`（紫色，`flex:1 1 100%` 独占一行）。

### 教训（重要，下次写归因类 UI 必守）
- **加总归因等于没有归因**：多个维度求和成一个数字，学生无法定位责任。凡是要解释"哪一项"，就必须逐维度列。
- **颜色语义必须绑定 `higherIsRisk`，不能绑定数字正负**：双轨计分里"+5"可能是坏（风险）也可能是好（创业），用符号上色必错。
- **归因行要考虑选项文字重复**：不同章节可能有字面相同的选项，必须带章节/节点标签区分。
- **测试脚本自身的坑**：Playwright 里 `$$` 拿到的句柄在 DOM 重建后会失效（"Element is not attached to the DOM"）。每轮重新用 `>> nth=N` 查询，不要缓存句柄。
